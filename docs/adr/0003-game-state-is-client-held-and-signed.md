# 对局状态由客户端持有并签名，服务端无状态

> **2026-08-22：「服务端不保存任何东西」这一句有了一处例外**，见
> [ADR-0006](0006-transcript-retention-for-the-pivot.md)（落对局语料）。
> 本文其余部分不变：对局**状态**仍由客户端持有并签名，服务端仍不存会话，
> 重新部署仍然不踢任何人下线。

对局状态（信任度、轮次、对话历史、已用钥匙、蓄势池）由前端持有，每轮随请求回传，服务端以 HMAC 校验完整性后求值，再签发新状态。服务端对局链路不保存任何会话数据。

决定性理由是部署节奏：投票期内会反复重新部署以持续迭代，任何驻留在进程内的对局都会在每次部署时被清空、把正在玩的人踢下线。而对话历史本来就要每轮全量发给模型，服务端并不需要"记住"什么——它只是个求值器。

Redis 仅承担旁路职责：开场白缓存与全局统计。**Redis 不可用时对局照常进行**，只是统计停止累加。

## Consequences

- 重新部署对进行中的对局零影响，可随时上线新版本。
- 无法防止重放：玩家保存旧的状态令牌即可回档重试。单机体验下可接受，**但这意味着不能做排行榜**——排行榜需要服务端权威状态，与本决策直接冲突。
- 请求体随轮次增长（12 轮中文历史约数 KB），在预算内。
- 签名密钥需随部署稳定；密钥轮换会使进行中的对局失效。
